# ServiceTitan 自愈循环——报告指标迁移的案例解读

**素材来源。** ServiceTitan 首席 AI 工程师 David Stein 在 QCon 的演讲，InfoQ 编辑整理（宇琪编译，Tina 策划）。演讲页：[Refactoring with AI Agents](https://www.infoq.com/presentations/refactoring-ai-agents/)。下面先记演讲里能核对的事实，再接到本书已有的关节。演讲里的类比留在案例里，不拿来当判断的句子。

**用途。** 这场迁移是「生成已经便宜之后，限速转到验证」的一个活样本。接到控制闭环、可证伪、划小圈、扬长、目标须外给，以及 [老底与新刃](../书稿%205/走向真实的交易/老底与新刃.md) 里的 Harness。与 [宁德时代曾毓群——全书框架的压轴综合案例](宁德时代曾毓群——全书框架的压轴综合案例.md) 并列，那一篇是整套框架在一家公司身上合奏，这一篇只钉一条工程回路。

## 一、案例里能核对的事实

### 要迁的是什么

ServiceTitan 给承包商和技工行业做端到端平台，覆盖住宅、商业、施工、电工、管道、暖通、屋顶、车库门。演讲前半顺带了他们在卖的几件 AI：按工单价值安排派工、漏接来电后再提醒回拨、7×24 的语音预约。Stein 明确说，这些不是这场谈的对象。

对象是报告指标。客户用这套系统下载和查看运营、财务及其他业务指标，底下是工单、发票、技术人员、客户。代码是遗留的：有些组件接入生产库的方式，和今天从头建会选的方式不一样。规模是几百个指标。每个指标后面一块代码，有的写于五到十年前，作者已离职，文档不全，单元测试覆盖差。合在一起是几十万行。依赖有的在架构上，有的是隐性的：对表结构的假设，对数据形态的默认依赖。

他划开的边界：不是数据库格式互相转换、写个脚本就能一键过去的那种。那种简单问题早就有人做完了。

目标是把这些指标迁到基于数据湖仓的新架构，具体平台是 DBT MetricFlow 和 Semantic Layer。报告系统上此前已经有过不止一次重构和迁移的尝试。这一次，团队先按人的方式拆遗留代码，时间线一直在挣扎：投入几个月甚至几年之后，进展和起初的预期对不上，于是开始怀疑方向本身。他们这时才拿当时最前沿的编码模型去看同一批代码，问能不能换一种推法。

按旧排期，这是成百上千张 Jira、数百个工程师周、几个季度到数年。此类项目常常必须走完，停在四分之一或一半不算结束，所以半路走不通的代价很大。价值要到结束才完全兑现，排期本身就极难。

### 整库丢进 Cursor 或 Claude Code，不行

到 2025 年，默认念头是把几百个指标直接丢进 Cursor。他试过，结果很差。原因和一名工程师无法独自改完几十万行相同：任务太大。人会挖出一点进展，然后面对一座缺少上下文的山，队友走了，文档没有，只能一寸一寸挖。

换成模型，失败的样子是另一套：幻觉，误解任务，发明新指标而不是迁移旧的；做完五个就停，说剩下的会按这个方式做，而那五个还是错的。当时最强的模型也是这个样子。

由此得到的做法，他自己说不是新想法：高级工程师和架构师每天都在把大问题拆成可执行的子任务。新的是把时间线反过来。

以前的大型迁移是：大量前期调查，做概念验证，看方案能否映射到现有技术栈、能否盖住需求，再决定买商业软件还是选开源，组团队，然后进入很长的批量迁移。现在是把前期的验证做严，严到每一个增量都能判定它是否做成了该做的事。几百个步骤可以并行，压进更短的窗口。全部价值更早到达。另一份更早到达的东西是信号：新方案若走不通，几周内能知道，不用等几个季度。

他用「迁一个指标」把人工步骤摊开，作为后面自动化的对照。工程师需要的上下文是：旧代码在哪，依赖哪些表，数据的真实样貌，分片，以及架构师已经定下的目标模式——新平台里这个指标该怎么摆。然后才是规划改哪些文件、怎么改，写代码，验证，写测试，发布。不论整次迁移是 5 步还是 500 步，范畴一样：架构目标展开成这些子任务。以前这些步骤进 Jira。现在若把取上下文、提示和验证都标准化，并且每一步都能以足够高的确定性判断是否真的完成，这些任务就可以交给机器，速度就不是按人周排的。

### 组装线

他把这套模式叫做组装线。前两步人本来就会做，只是做法不同；2025 年水平的编码模型把第三步自动化。

第一步是分解。不要问「怎么把整座山搬走」。要精确到「怎么搬走一块石子」：用实验证明，一个 agent 确实能独立完成这一小步。石子这个粒度若不合适，就继续用实验改，直到粒度对上。

第二步是验证，他称为最关键的一步。每个子任务要有一个可以程序化判断通过或失败的脚本、环境或平台，bot 的每一次尝试都能被精确验收。并行跑大量任务时，若不知道每一步是否真的好，偏离会很快。他回头问过自己：以前把同样的任务派给高级工程师时，为什么没有坚持用这么严的、可编程的验收。Joe 或 Alice 提交 PR 时，本可以有一套清晰的验证，保证产出符合预期；他过去很少见到有人这么做。用 agent 把迁移加速之后，这件事从可有可无变成必需。

他们做的验证器是一个小型模拟器：用新的指标平台生成并保存报告，使这些报告能和后端报表系统的报告对照。要保证格式正确、数据可以直接比、能扫过分布、数字对、格式对。他管这个能实际测试 agent 产出的环境叫「物理引擎」。遗留系统往往不好观测，和不好做单元测试是同一类困难：时序、数据对齐，不一定能在该看的时刻拿到该看的数据。这些能力以前像锦上添花，在这条回路里是必要条件。几百个指标迁下来，验证器改过多次。项目里大部分工程精力花在把这个模拟验证脚本做扎实。原文没有给出百分比。

第三步才是写代码。任务要彼此相似，这样同一套上下文能反复用。很多任务都需要的一种上下文，是 staging 里 Snowflake 集群中的真实数据。这次迁移完全没有用 MCP，在 CLI 上工作，和工程师取上下文的方式一样。只告诉模型「把这个指标的公式在新平台上重写一遍」、却不给表里数据的实际样子，它写不出正确的代码，人和模型在这一点上一样。

具体配备是这些：

- SnowSQL：从命令行跑 SQL，连接 Snowflake。凭证只开到暂存数据，让它能看见指标底层表长什么样。
- 已有迁移构件在哪里，方便它找可以复用的东西。
- 检查自己工作的方法，必须和工程师验证时用的方法一致。范围限定在当前任务，不去干后面的任务。
- `migration_goals.txt`：Goal State。整体迁移在什么条件下算成功，每一步的进度如何，而且写成配备的工具能检测到的状态。问答里他把同一份思路又称为 `goal_state.txt`。
- `migration_tasks.txt`：任务的详细拆解，分成多个阶段，留给工程师做检查点。

在 Cursor 里，提示不再是「做这个」，而是：熟悉 `migration_goals` 和 `migration_tasks`，然后实现阶段 2.3。Cursor 自己生成待办，再把一两项指标拆开。粒度仍然要人把住。提示保持简单，复杂藏在验证步骤和工具后面，并保证它手里有解决问题所需的上下文。

前 10、20、30 个任务反复重做，直到验证脚本、上下文和工具都打磨到位，然后放手。短短几周里，它几乎做完了其余任务。每完成一个指标，就在文件里标为已完成。人通过每次提交看这个文件，进度是逐步可见的。

### 自愈循环，以及验证不够时

单个任务上的回路是：agent 用配给的工具取上下文，写代码，跑验证器。不满足，就看不匹配的细节，再试。验证器和取上下文一起转，迁移才转得下去。

最初几次把飞轮转起来，最大的问题是验证不够好，事情会以很快的速度失控。他分开的三种情形是：

- 上下文不够，bot 卡在某个任务上。
- 模型读不懂写于很久以前、文档残缺的代码，在特定任务上挣扎。这时要改的是上下文怎么呈现。他把这一步看成可控的迭代：最坏是推不动，然后回头改呈现，不是一次不可控的赌博。
- 验证器不够精确。agent 会长时间一个接一个地跑，最后得到一堆看起来合理、实际上是垃圾的结果。没有真正好用的验证器就无法推进，可能浪费一整天甚至一周的计算，然后发现没有达标。

他给「要多聪明」的回答是：不必像人类工程师，也不必是去年那种短上下文窗口就一定不行——限速不在智商，在这条自愈工作流。他听到的担心是幻觉、低级错误、写出来的代码不敢放上生产。他的回应是：它们根本不需要那么聪明。

他用的类比是 1990 年代的游戏《百战小旅鼠》：那些旅鼠很笨，人在路线上放路障，它们就能到终点。组装线就是这些路障，`migration_goals.txt` 是用工具能检测到的状态画出来的路线。InfoQ 正文里「赫拉克勒斯式的任务」是编辑对「极其艰巨」加的注，不是他的类比。

### 跑出来的数，和两类翻车

报告平台的大量指标按这个流程跑过。他给出的覆盖是：大约 15% 的指标太复杂，必须工程师亲自介入；85% 的脏活可以由自动化盖住。几百个指标时，这个比例才有意义。周期从几个季度压到几周。

另一件他强调的事：迁到一半发现架构不好，想推倒重来。在 Jira 工单的做法里，这是时间和士气的重击。改好规则再跑一遍，执行体不在乎。他用自己的职业生涯作对照：加入 ServiceTitan 之前，2012 年到 2023 年在 LinkedIn，见过跨地域的 active-active，也见过把巨大单体拆成微服务，几十甚至上百名工程师、连续多个季度。他认为能写代码的 agent 带来的变化，不只是单个任务更快，而是那些因为工单太多、季度太长而一直不做的事，变得可以试。

他归成的翻车，和上面三种情形对得上，案例里讲得更具体的是两条：

1. Agent 以为自己成功了，报告完成，验证脚本一查，逻辑不对。对策就是把验证做扎实。大部分工程精力花在这里。
2. Agent 卡住。常见原因是找不到能覆盖某条微妙逻辑的测试数据，例如依赖一段特殊时间或某种数据密度，示例里扒不出来。这是信息不够。对策是回到源头做一份「黄金清单」：含优质测试数据的 ID，以及数据密度已知的时间范围，写进 `migration_goals`。以前是隔着工位问同事「你测那个指标用的什么 ID」。他把这类东西称为部落知识。写进上下文之后，成功率上去。

### 问答里他补的两句

若再做一遍，最短路径是什么，能不能只靠 Copilot、Cursor 现成的能力把工作流压到极致。他的回答是：以现在能做到的，这套流程还能再简化，但更简单的方法他还没有。Cursor 和 Claude Code 正在把人往类似的方法上引，只是验证器和类似物理引擎的机制未必做得这么正式。他预计以后可以直接把整个问题丢给 Cursor，让它自己分析遗留代码、造出验证器和模拟引擎；那一天之前，还是要把问题拆到 Claude 4.5 Opus 或其他顶级模型能够完成的粒度，把任务定义清楚，搭一个可靠的验证器，再按上述流程启动。

安全与隐私：他们的做法是严密监控，并且只给 staging 数据。不把生产数据库的密钥交给 agent，也不给能够删除线上数据的权限。他认为即便 Cursor，安全隔离也仍在成熟。敏感场景里，要决定配置哪些工具、跑在什么环境；这套限制的严格程度可以按业务往上加。

## 二、接到本书

事实如上。下面是解读，不再添演讲里没有的比例。

主启示：当生成变便宜，验证就成为新的稀缺；这条回路的上限，由验证的严密度和任务能否被判定决定，不由执行体的智能决定。

**自愈循环是控制论闭环，并把回路里的等待自动化。** 「生成 → 验证 → 不通过则看差异并重来」就是侦察、判断、决心、部署，也是 [孤独不是姿态](孤独不是姿态，是对洪流关闸——AI时代五杠杆的稀缺逻辑.md) 里纠错迭代那条杠杆。季度压到几周，秘密不在模型突然变聪明，在验证这一环不再等人。限速器是回路时延。错得快、改得快，在这里被做成了可以开动的流程。

**大头精力放在验证上，是可证伪判据上移。** 这正是 [一根矛盾，一串需求](../书稿%205/走向真实的交易/一根矛盾，一串需求.md) 的可证伪判据，也是 [数学精神与科学方法](../关键文章/学科/数学精神与科学方法.md) 的可验证、可复现。生成的边际成本趋近于零之后，价值从「产出答案」移到「检验答案」。自动裁判成为那道坎。谁有严密的验证，谁才能把不完美的生成用起来。

**原子化加上可编程验证，是划小圈，并且切在缝上。** 「拆成 agent 能独立完成、并且必须能判定的微任务」是 [塑造技能的机理与内容无关](../书稿%205/总论/3.2%20塑造技能的机理与内容无关.md) 的划小圈，再加一条硬约束：可判定。[庖丁解牛的三层](../书稿%205/庖丁解牛的三层——目无全牛·以无厚入有间·出神入化.md) 里，刀从缝里过。可判定的粒度，就是自动化能到达的边界。15% 要人介入，正是切不出可编程裁判的那一部分。粒度本身也是实验出来的：前几十个任务反复重做，是在找缝，不是在展示模型。

**不升级执行体，升级它所在的场。** 「不必像人类工程师那么聪明」是 [扬长——选生态位、配假肢与拧长板](../书稿%205/走向真实的交易/1.2%20扬长——选生态位、配假肢与拧长板.md) 的系统版：别等执行体变强，去改验证、上下文和部落知识的文档。有限的执行体在可靠回路里重复，就能盖住那 85%。可以收成一句：**笨执行体加上严密验证，胜过聪明执行体加上松散验证。** 松散的那一侧，演讲里的样子是一堆看起来合理的垃圾，以及白烧的一天到一周算力。

**上下文是把目标从外面给进去。** `migration_goals.txt` 写成功标准，黄金清单把「你用的什么 ID」写成文件。这印证 [点是面向目标的投影](../书稿%205/点/点是面向目标的投影——不是知识的内禀属性.md)：模型能生成代码这一点，给不了目标轴。成功标准和测试数据这些隐性判据，要显式写成它能用的语言。上下文工程在这里就是把人的判据翻译成机器跑得了的判据，也是 [表达不为还原](../书稿%205/表达不为还原——面向目的与主体的行动.md) 的一次现身：对方是 agent，留下的是服务这一步验收的那几句。

**对本题，这是把大模型嵌进系统的一个活体。** 尖刀骨是系统可靠性对变化的速度，尖刀是把大模型可靠地嵌进系统，新刃里有 Harness 工程（[老底与新刃](../书稿%205/走向真实的交易/老底与新刃.md)）。生成提供变化的速度，验证提供可靠性，自愈循环是两者咬在一起的方式。问「可靠地嵌进去是什么意思」，可以用这场迁移回答：大部分工程精力放在可编程验证上，任务拆到一次能验收的粒度，模型不完美，回路仍能把几百个指标里的大部分迁完。

## 诚实的边界

用 [同构判据](../书稿%205/总论/2.2%20同构判据——功能·机制·结构，两旋钮与四问.md) 的第四问收一下。这套方法的切面，是能造出可编程裁判的任务。代码迁移可以对照测试通过、对照黄金数据，天然可判定。切面之外，开放式设计、审美、没有客观裁判的新问题，这条循环转不起来，因为没有东西可用来判通过或失败。

安全上，演讲自己的边界也很窄：staging、不给生产密钥、不给删除线上数据的权限、人在旁边看。隔离做得再严，也是这条回路的一部分，不是模型变乖之后可以撤掉的。

所以这里新的稀缺技能，是能不能为一个有价值的任务造出可靠的裁判。能，有限的模型就进得了回路；不能，再强的模型也只是开环在转。

---

一句话收：这场迁移把问题从「模型多聪明」搬到「验证多严密、任务多可判定、上下文有没有把人的判据写出来」。生成已经便宜。裁判和粒度，才是这条组装线转不转得动的地方。
